# GitRoast: research and design for sharper, less repetitive roasts

Reviewed 2026-09-27. This is a source-backed design proposal, **not** a measured claim that any prompt or model is funnier. “Source” below means an official API document or an original research paper; “Recommendation” means an engineering/editorial inference to test in this app.

## Implementation status in this working tree

The diagnosis below describes the starting implementation. The working tree now curates up to four featured repositories from top stars, recent pushes with traction, newest creation, and oldest creation. Accounts with over 100 public repositories get bounded additional creation-sorted pages and a star-sorted search. The curated repositories receive best-effort README, root package, and complete-tree inspection; two can receive release data and one an authored commit's reported change scope. The fallback uses evidence-ranked angles, concise verdicts, original optional film/book allusions, and distinct premises across visible sections. The model input includes a report-wide section plan, and the configured default is now `gpt-6-sol` at low reasoning effort. Linked receipts, stronger claim checks, corrected commit/inactivity classification, and revised share/UI copy complete this implementation pass. The synthetic eval runner and automated checks pass. A live model comparison, human humor ratings, claim-level semantic verification, and inspected commit patch *contents* remain recommendations, not completed or measured gains.

## Diagnosis from this repository

1. **The model has little access to the work itself.** [`lib/github.ts`](../lib/github.ts) fetches profile/repository metadata, an Atom-derived set of commit *subjects*, and contribution-calendar data. [`lib/repository-evidence.ts`](../lib/repository-evidence.ts) optionally adds a short README excerpt, root `package.json` counts/scripts, and latest release for only the first two repositories. It never inspects a file tree, test file, implementation, or commit patch. The prompt asks for a brutal review of public work, but most available facts support jokes about descriptions, stars, quiet repositories, and commit titles. This is an inference from the local code, not a statement about GitHub's data limits: GitHub offers repository contents, trees, and individual commits with changed files/patch data for public resources. [GitHub repository contents](https://docs.github.com/en/rest/repos/contents), [Git trees](https://docs.github.com/en/rest/git/trees), [commits](https://docs.github.com/en/rest/commits/commits).
2. **A successful model call still leaves prominent stock copy.** [`normalizeReport`](../lib/openai.ts) always supplies `receipts: repoAwareReceipts(summary)`. [`lib/roast-copy.ts`](../lib/roast-copy.ts) repeats courtroom, archaeology, missing-description, and “future maintainer” setups across fallback sections. [`components/roast-report.tsx`](../components/roast-report.tsx) adds fixed jokes in stats, empty states, and the footer. [`components/share-card.tsx`](../components/share-card.tsx) prefers the deterministic commit receipt as its `bestSignal`. A prompt rewrite alone cannot change those surfaces.
3. **The current guard is lexical, not editorial.** [`repeatsJoke`](../lib/roast-quality.ts) uses word-set Jaccard overlap. “The README left no clue” and “Documentation is playing hide-and-seek” can pass while making the same joke. [`isGroundedInRepository`](../lib/openai.ts) can accept a line because it includes a repository name and *any* available anchor; it does not prove the actual claim. Structured Outputs constrains JSON shape, while OpenAI explicitly says structured outputs can still contain mistakes. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
4. **There is an evaluation harness, not quality evidence yet.** [`eval/roasts.test.ts`](../eval/roasts.test.ts) exports blind reports for 20 synthetic profiles and a blank human-rating CSV. Its offline mode checks fallback shape and provenance. [`docs/roast-quality-and-snark.md`](roast-quality-and-snark.md) explicitly records that no live model winner or human humor rating has been measured. The starting `gpt-4o-mini` default, `0.85` temperature for GPT-4-family IDs, 2,400 output-token ceiling, and 16-second generation ceiling were choices to test, not known optimums.

## Product target: a funny review that can show its work

**Recommendation.** Make every publishable line contain (a) a verified artifact-specific observation, (b) an actual critique or earned praise, and (c) a surprising comic turn. A line that could be pasted onto ten unrelated profiles fails even if it mentions a repository name. The “brutal” target should be a concrete mismatch in the *work*—promise versus implementation, documentation versus setup, commit title versus diff, release story versus repository state—not the developer's worth or life.

An original psychology study found amusement when a violation was also perceived as benign in its moral-judgment experiments. Applying that result to code-review roasts is an **editorial hypothesis**, not a validated humor formula: the violation can be the work's contradiction, while the benign frame is a playful pull-request review with accurate receipts and no identity attacks. [McGraw and Warren, 2010](https://journals.sagepub.com/doi/10.1177/0956797610376073).

Examples below use **fictional evidence**, not claims about a real user:

| Observed evidence | Generic line to reject | Better candidate and why |
|---|---|---|
| `deploy-now` README says “one-command deploy”; its documented setup lists seven required environment variables | “Your docs need work.” | “`deploy-now` offers one-command deployment after a seven-variable opening ceremony.” The punchline is the inspected contradiction. |
| A commit titled `tidy up` changes the retry policy and adds an outage regression test | “Vague commit messages.” | “`tidy up` quietly rewrote the retry policy and added an outage test. The commit title dressed a fire drill as housekeeping.” The critique concerns title versus observed patch. |
| A small library has clear tests and a tagged release, with few stars | “Only 8 stars? Yikes.” | “Eight stars, a release, and tests that explain the edge cases. The internet's applause budget is the least interesting metric here.” The review recognizes actual work. |

## Recommended pipeline

### 1. Build a typed, bounded evidence ledger before prose

**Source fact.** GitHub's contents API can read files and READMEs, its Git-tree endpoint can enumerate paths, and its commit endpoint returns changed-file metadata and may include patches; public resources are accessible without authentication subject to API constraints. A recursive tree response can be truncated, so the caller must treat that case as incomplete. [Contents](https://docs.github.com/en/rest/repos/contents), [trees](https://docs.github.com/en/rest/git/trees), [commits](https://docs.github.com/en/rest/commits/commits).

**Recommendation.** Select a *diverse* set of repositories rather than just the first two by update order: one strongest/most distinctive, one active, and one revealing contrast, with a tight request/byte/time budget. For each selected repo, inspect README claims, root tree, one or two manifest/workflow/test files when present, and at most one representative public commit patch. Prefer a cross-file contradiction (e.g., “zero config” versus documented env vars) to a raw metric. Do not infer “no tests,” “broken CI,” bundle size, ownership, code quality, or production usage from missing, inaccessible, or partial data. Label fetch status `observed`, `not_found`, `unavailable`, or `not_inspected`; only `observed` supports a positive claim, and `not_found` must be scoped to the exact queried path. Keep original source URLs, path, ref/SHA, and short excerpt in each fact so the report can show a receipt. Skip secrets, generated files, lockfiles, and huge diffs.

Suggested internal representation:

```ts
type Fact = {
  id: string;                 // e.g. "repo:deploy-now:readme:setup"
  subject: string;            // exact repository or commit
  claim: string;              // narrow, literal observation
  sourceUrl: string;
  sourceKind: "metadata" | "readme" | "tree" | "file" | "commit";
  status: "observed" | "not_found" | "unavailable" | "not_inspected";
  confidence: "direct" | "derived";
};
```

### 2. Select **angles**, then allocate them across the whole report

**Recommendation.** Turn fact pairs into angle cards with `factIds`, `critique`, `comicMechanism`, `safetyRisk`, and `distinctiveness`. Mechanisms can include contradiction, understatement, literal interpretation, escalation, inversion, and reluctant approval. Score for specificity and surprise; reject angles whose claimed defect is not evidenced. Allocate one dominant angle to the opening verdict, different local angles to repositories, commit-title/patch mismatch to commit reviews, score methodology to the score caption, and a practical response to the strongest critique for redemption. Let receipts explain evidence rather than repeat each punchline. If two sections depend on the same missing-description fact, keep the stronger line and give the other section a different fact or a plain factual sentence. One intentional callback can work if it changes meaning.

Current `buildRoastAngles` produces only a few angle types; the prompt instructs variety but does not reserve premises. The report schema asks one model call for more than twenty text fields across several sections. A useful experiment is **angle planning → drafting → verification** with the plan kept internal and the public response shape unchanged. This is a proposed architecture, not an OpenAI requirement. OpenAI advises supplying relevant context and clear instructions; its structured-output guide explicitly suggests splitting tasks when mistakes persist. [Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

### 3. Draft with evidence IDs, then verify claims and repetition

**Recommendation.** Keep strict JSON schema, but make the *internal* draft schema carry `factIds` and `angleId` for each line. Validate that IDs exist, referenced facts are observed, the line does not assert an unobserved defect, and each section uses its assigned premise. Grounding needs claim-aware checks or a bounded semantic reviewer: the current presence of a repo name or language does not verify “its CI is broken.” Reject unsupported lines rather than repairing them by inserting an anchor word. Preserve exact repository names and commit subjects. Return explicit `insufficient_evidence` for a section instead of inventing a flaw.

For diversity, compare normalized **angle IDs and premises** first; lexical similarity is a second guard. Maintain a small motif blacklist for recurrent in-house tropes (“courtroom,” “archaeology,” “mystery department,” “side quest,” “future maintainer”) based on actual evaluated repetition, not an ever-growing generic ban list. Review the entire rendered report, including deterministic receipts, stat captions, empty states, and share text, before delivery. Structured Outputs is appropriate for reliable fields but is not a truth or humor validator. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

### 4. Make fallback and share surfaces first-class editorial output

**Recommendation.** The current deterministic fallback should be a smaller evidence-aware report, not a full set of repeated stock jokes. When source data is thin or the provider fails, show one or two strong observed comments and honest “not enough public evidence” states; do not pad all sections with courtroom filler. Let `receipts` carry verified evidence and an optional *distinct* kicker. The share card should choose the highest-rated concise line from any section (within export limits), instead of always preferring its stock commit receipt. The public score may remain deterministic, but critique the score's *observed factor imbalance* and disclose that it is an app-defined score.

### 5. Tune model, effort, and candidate selection against quality data

**Source fact.** OpenAI says model behavior varies by snapshot, recommends pinned production snapshots with evaluation on changes, and recommends task-specific evals plus human judgment. Its model selection guidance distinguishes quality, latency, and cost; reasoning effort is model-dependent. [Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering), [evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices), [model selection](https://developers.openai.com/api/docs/guides/model-selection), [reasoning models](https://developers.openai.com/api/docs/guides/reasoning).

**Recommendation.** Blind-test the current default against at least one stronger currently available model and an improved-prompt control **on the same evidence packets**. Compare one-shot drafting with two distinct candidates and a claim-aware selector; candidate search may improve the best line but doubles generation cost and can exceed the 16-second budget. Test low versus medium reasoning effort where supported and measure output truncation, refusal, repair, latency, token use, and cost per *accepted* report. Do not assume higher temperature, maximum effort, fine-tuning, or “more brutal” adjectives creates originality. Pin the chosen model snapshot and version the prompt/evidence schema/cache together. OpenAI's hosted Evals and fine-tuning surfaces currently carry deprecation notices, so retain the repository-owned eval harness rather than betting the workflow on those services. [Model optimization](https://developers.openai.com/api/docs/guides/model-optimization), [evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices).

## Quality gate: measure humor, not only valid JSON

**Source fact.** OpenAI's evaluation guidance calls for representative data, human calibration of automated grading, and pairwise/pass-fail comparisons; it warns that model judges can have response-order and verbosity bias. [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices).

**Recommendation.** Extend the 20 synthetic cases with consented real public-profile snapshots from distinct archetypes (sparse, well-maintained, popular but poorly explained, archived, polyglot, long-lived, and intentionally adversarial source text). Preserve a fixed snapshot per comparison and stratify by evidence richness. Have at least two human raters blind-review whole rendered reports **and** the top share line. Randomize model labels and response order, keep lengths comparable, resolve disagreement explicitly. Score: factual grounding (hard gate), artifact specificity, critique accuracy, laugh/surprise, cross-section premise diversity, taste/shareability, and useful redemption. Capture whether a rater can identify the exact repository/commit behind the joke. Add automatic gates for fact IDs, exact identities, unsupported negative claims, repeated `angleId`, banned personal attacks, and fallback rate. A model judge can triage candidates only after it agrees with human labels on a held-out set.

Proposed ship gate (a **target**, not a result): zero invented work claims or personal attacks in the manually reviewed set; at least 80% of lines judged both specific and grounded; fewer than 10% of reports with a repeated premise across sections; and a statistically credible pairwise win over the current app on laugh/surprise without worse taste. Log prompt/model/evidence version and aggregate failure categories; avoid retaining raw usernames or source text unless there is an explicit product reason and retention policy. The current telemetry already records coarse generation outcomes without those raw inputs.

## Tone and safety boundaries

**Recommendation.** The copy can be savage about a repository promise, a visible diff, setup friction, or a documented contradiction. It should never claim the author is stupid, unemployable, mentally unwell, dishonest, or privately inactive. Sparse public evidence calls for a short, self-aware review, not invented code defects. Positive evidence can support a reluctant approval; reflexively making excellent work sound bad weakens both credibility and humor. Reject slurs, identity/appearance/relationship attacks, profanity that undermines sharing, and unsupported claims of security defects or broken software. Preserve the user's request for sharper roasts by aiming severity at the artifact and specificity, not at the person.

**Source fact.** OpenAI recommends adversarial testing and input limits for prompt-injection exposure, and offers moderation signals for generated content. Moderation is a safety signal, not an assessment of joke quality; the application still needs its own artifact-target/taste rules. README and commit text are untrusted inputs and should stay in data fields, not become instructions. [Safety best practices](https://developers.openai.com/api/docs/guides/safety-best-practices), [moderation](https://developers.openai.com/api/docs/guides/moderation), [prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering).

## Implementation order

1. Build a **baseline**: run live candidates with existing fixtures, add a small real-profile set, and obtain blind human ratings. Record exactly which visible lines were deterministic and where the same premise recurred.
2. Replace stock receipt/share selection and UI joke copy with a report-wide premise inventory and evidence-aware fallbacks. This directly addresses repetition even on provider failure.
3. Add bounded work inspection and typed source facts, starting with representative READMEs, tree paths, and one carefully selected commit diff. Expose source links in receipts and enforce unknown versus absent.
4. Implement angle allocation, internal fact-ID output, claim checks, and a selective editorial repair that sees already-used premises. Keep the public API shape unless the UI needs source links.
5. Blind A/B the prompt/workflow/model variants; ship only the candidate that clears factual/taste gates and wins on humor at acceptable latency/cost. Continue to sample live outputs for drift.

The highest-leverage bet is **more meaningful evidence + one report-wide editorial plan**. The degree of humor improvement remains an empirical question until the blind review is filled in.

## Follow-up research: profile curation and sharper original comedy

### Curate a deliberately mixed repository set

**Source facts.** GitHub's public user-repository endpoint supports `sort=created|updated|pushed|full_name`, `direction=asc|desc`, `type=owner|all|member`, and at most 100 repositories per page; it does **not** offer a star-count sort. Its repository-search endpoint supports `sort=stars|forks|help-wanted-issues|updated`, and `user:USERNAME` scopes a search to an owner. GitHub's `pushed` criterion means the latest commit on *any branch* of a repository; it does not establish that this profile owner authored it. Pagination uses `Link` headers, and unauthenticated REST calls share a 60-request-per-hour limit by source IP; search endpoints have more restrictive limits. [List repositories for a user](https://docs.github.com/en/rest/repos/repos#list-repositories-for-a-user), [search repositories](https://docs.github.com/en/rest/search/search#search-repositories), [repository search qualifiers](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories), [pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api), [rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).

**Recommendation.** Reserve slots before any roast-worthiness reranking: most starred owned original, newest created owned original, hottest recently pushed owned original, and oldest created owned original. Fetch `created desc`, `created asc`, and `pushed desc` heads (e.g. 100 each), plus a scoped star-sorted search or all owner pages for the star leader. Dedupe by repository ID and backfill from the next candidate in each lane so a profile with only a few originals degrades gracefully. Treat `updated_at` as a separate metadata signal, not the activity lane. Label the lanes in the report and avoid calling a sampled repository the account's *most* starred unless the star-sorted search or complete inventory proves it. If a recent push comes from another author, describe the repo as recently pushed and inspect an authored commit before making a claim about the profile owner's own work. Track request count, page completeness, and the sampled-universe size as part of provenance. The slot recipe is a product choice to test, not a GitHub-defined ranking.

### Use film and book references as lenses, not reusable punchlines

**Source facts.** A study of linguistic incongruity found that ambiguity and distinct viewpoints predicted human funniness judgments for puns; that result does not prove a formula for code roasts. A 2026 computational-humor study found that semantic novelty measures correlated with expert originality ratings, but only moderately, so a novelty score cannot replace a human comic judgment. [Kao, Levy, and Goodman](https://web.stanford.edu/~ngoodman/papers/KaoLevyGoodman.pdf), [Amir et al., CHum 2026](https://aclanthology.org/2026.chum-1.8/).

**Recommendation.** Build the joke from a verified repository contradiction first, then optionally choose a *fitting* narrative lens (heist, courtroom, detective story, space opera, haunted house, epic quest) that sharpens that contradiction. The connection should explain the work: a claimed one-step installer with seven setup prerequisites may earn a heist-planning comparison; a clearly scoped one-file fix does not. Rotate mechanisms across the report and across profiles; do not add a movie name to an otherwise generic line. Keep a reference budget of at most one prominent allusion per report, no recurring franchise as an app catchphrase, and a plain fallback for readers who miss the reference. Test reference-bearing lines against equivalent original metaphors in blind human review; a name-drop is not evidence of higher humor quality.

The U.S. Copyright Office says names and titles and short phrases are generally outside copyright protection, while its fair-use FAQ treats copying a passage as contextual and case-specific. **Editorial inference:** invoke a title or a broad genre when it earns its place, but write fresh wording rather than reproduce recognizable film dialogue or book passages; avoid presenting a reference as an actual quotation. This is a practical content rule, not a guarantee about every jurisdiction or trademark use. [Copyright Office regulation](https://copyright.gov/title37/202/37cfr202-1.html), [fair-use FAQ](https://www.copyright.gov/help/faq/faq-fairuse.html).

For roast evaluation, add separate human ratings for *punch*, specificity, surprise, reference clarity, and taste. Check repeated **comic mechanisms and premise pairs** across the entire rendered report, rather than only repeated words. A semantic novelty measure may help surface stale candidates for review, but the current study's moderate correlation calls for human calibration and a factual-grounding gate before publishing. [Amir et al.](https://aclanthology.org/2026.chum-1.8/), [OpenAI evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices).
